> Companion document to `docs/SYSTEM_ARCHITECTURE.md`. Produced by three parallel deep-code audits (Auth/RBAC/Multi-tenancy/API; Business Logic/State Machines/AI-Drishti; Reliability/Offline/Files/Deployment/Testing), each independently tracing execution paths with file:line evidence, cross-checked against the codebase at branch `predef-pts`. ## 1–3. Security, Authentication, Authorization — Summary

**Authentication is sound.** JWT uses pinned `HS256` (no `alg=none` risk), access-token authorization re-fetches the user's role/org from the database on every request rather than trusting token claims (regression-tested: `test_forged_role_claim_is_ignored`), refresh tokens rotate and revoke via Redis-backed `jti` tracking (degrades to single-instance-only in-memory if Redis is unreachable — see F6), and password-reset tokens are invalidated atomically on use (`repositories/user.py:81-88`), preventing reuse. Self-registration is hard-capped to role `"user"`; privilege escalation via self-role-edit, self-demotion, and last-admin-removal are all blocked and tested.

**Authorization has one critical gap (F1) and one high-severity gap (F2)** — both detailed below. Everywhere the codebase *does* implement project-scoped RBAC (`drishti.py`, `construction_progress.py`), it does so correctly via `RBACService.get_accessible_project_ids`. The gap is that this pattern was not applied uniformly to `workflow.py`.

## 5. Business Logic — AI vs. Deterministic Decision Boundary

**Construction-progress pipeline:**
- **AI (vLLM/vision model) decides:** per-surface-group `completion_pct`, `confidence`, `evidence_class`, and free-text `evidence` per activity, from photos (`vllm_provider.py` `_call_surface_group`, `_SYSTEM_PROMPT`).
- **Deterministic Python decides everything else:** which capture is "latest per pin" (`_dedupe_latest_per_pin`), evidence-class-to-percentage capping/zeroing (`apply_evidence_class`, `reconcile_pct_with_evidence` — hard-coded rules, not AI), per-unit merge via "incompleteness wins" (`prefer_lower_unit_evidence`), full-roster rollup math including 0%-for-uncaptured-rooms (`rollup_activity_over_roster`, `recompute_flat_finishing_pcts`), room/flat/floor status buckets, pin-to-room attribution (human-review corrections always take top precedence over AI), and final `overallProgressPct`.
- **Malformed AI output handling:** unknown `activity_id` → dropped; missing/non-numeric `completion_pct` with no legacy `state` → dropped entirely (never defaulted); `not_visible`/`NOT_OBSERVABLE` → skipped. A JSON parse failure raises and is caught per-capture as zero evidence (BIZ-2) rather than partially corrupting a snapshot write.

**Drishti — confirmed materially deterministic**, matching the commit-history claim of a rework away from LLM-driven search/calculation:
- **Only 2 LLM calls per turn:** (1) intent classification + rough scope-name hints (never an id, never a calculation) in `drishti_query_planner.py`; (2) final prose generation strictly over a pre-assembled, 100%-deterministic `facts_payload`.
- **Everything else — entity resolution, retrieval, ranking, rollups, forecasting — is pure Python/Mongo**, with fuzzy name matching guarded against ever trusting an LLM-invented id; unresolvable references become an explicit `not_configured` status rather than a guess.
- **Hallucination guardrail:** every answer is validated against a Pydantic schema before being returned, with one corrective retry and a fixed safe fallback string otherwise. Nothing the LLM outputs is ever persisted back into progress/snapshot collections — the blast radius of hallucination is bounded to phrasing of an already-fact-checked answer.
- **Tenant scoping:** `_assert_project_access` gates every project-scoped Drishti route via `RBACService.get_accessible_project_ids`, and every downstream retrieval call is explicitly keyed by the authenticated `org_id` — the LLM never supplies an org/project/floor id itself.

## 6. False-Positive / Mitigation Section (Investigated, Found Safe)

| Area | Why it looked risky | Why it's actually safe |
|------|---------------------|-------------------------|
| JWT claim tampering / `alg=none` / stale role after promotion | Tokens carry `org`/role-adjacent claims | `decode_access_token` pins `algorithms=[HS256]`; `get_current_user` re-fetches the user's live role/org from the DB on every request rather than trusting the token. Regression-tested. |
| Refresh-token replay after logout | Tokens are bearer, stateless-looking | Redis-backed revocation keyed by `jti`, rotated on every refresh. Degrades to single-instance-only if Redis is down (AUTH-5), but is not silently bypassable when Redis is up. |
| Password-reset token reuse | Reset tokens are typically a common reuse bug | `update_password` (`repositories/user.py:81-88`) atomically nulls `reset_token_hash`/`reset_token_exp` in the same DB update called from `reset_password`; a second use fails the lookup query immediately. |
| Concurrent project-assignment / registration races | Check-then-act patterns are common in the assignment flow | A genuine unique partial index on `user_projects{org_id,user_id,project_id}` (`db/indexes.py:42-47`) rejects true concurrent duplicates at the DB layer, independent of application-level races. |
| Self-role-escalation via registration or profile update | Role is client-suppliable in some payloads | Self-registration is hard-capped to role `"user"`; admin-assigned roles are capped by the caller's own role; self-demotion and self-deactivation are blocked; last-admin-standing guard is present. | Field-engineer cross-ownership of captures/tours | Captures/tours are created by individual users | `_assert_can_access_capture`/`_assert_can_access_tour` (`workflow.py:286-318`) enforce real ownership/org checks, backed by ~10 dedicated tests. |

## 7. Requires Runtime Verification (Not Settleable by Static Reading)

1. Whether `APP_ENV` is actually set to `production` on the live Render deployment (the manifest declares it; the live value wasn't observable).
2. Whether any **write/delete** media or capture endpoints share `media_access.py`'s org-blind authorization gap (AUTH-1) — this audit confirmed the *read* path only; a full sweep of mutation routes for the same class of bug is still needed.
3. Whether Redis is actually reachable/configured in production (both rate-limiting AUTH-4 and token revocation AUTH-5 silently degrade otherwise).
4. Real-world exploitability of AUTH-1 depends on how easily a sibling org's id can be discovered in practice (shared screenshots, support tickets, browser history) — worth a lightweight pen-test.
5. Whether currently-assigned manager/field_engineer accounts are actually multi-project, to gauge near-term exposure of AUTH-2 vs. latent risk.
6. Actual vLLM behavior under real malformed/timeout conditions (BIZ-2) — retry/backoff paths were read but not executed.
7. Whether `resequence_pins_on_plan` is ever invoked concurrently with `backfill_floor`/review submission in real traffic (affects BIZ-3's real-world likelihood).
8. Actual production disk-usage growth rate for `uploads/stitch_failures` (REL-4) — theoretical vs. near-term risk depends on real capture volume.
9. Whether Render's persistent disk (if any) survives redeploys — if `uploads/` is ephemeral storage, every local-disk capture is lost on each deploy regardless of job-recovery logic; not verified against actual Render disk configuration.
10. Real-world frequency of "logout while uploads pending" (REL-2), and whether token-expiry auto-logout can trigger it without explicit user action.
11. Whether `mongomock_motor`-based tests catch real MongoDB index/constraint behavior (e.g. unique-index violations) that only manifests against a real Mongo instance.

## 10. Final Audit Summary

**What is working well:** JWT/session design, password-reset security, registration/role-escalation guards, org-scoping helper (`_with_tenant`), unique-index-backed race protection on assignments, Drishti's deterministic retrieval pipeline with real hallucination guardrails, snapshot-purge-on-delete, review-reapply-on-reanalyze, dedup logic addressing a documented past incident, and a genuinely functional offline dual-queue on the frontend.

**Critical problems (confirmed):** cross-tenant media disclosure (AUTH-1); missing project-scoped RBAC across `workflow.py` (AUTH-2).

**Biggest security risks:** AUTH-1 (P0, cross-org data leak), AUTH-2 (P1, cross-project privilege escalation within an org).

**Biggest data-loss risks:** REL-2 (file-upload queue wiped on logout — confirmed, not recoverable), REL-7 (write-queue silent drop on localStorage quota — confirmed, not recoverable), REL-4 (unbounded disk growth risking app-wide upload failures if the disk fills).

**Biggest reliability risks:** REL-1 (two of three background-job families lack crash/redeploy recovery), BIZ-1 (duplicate analyze-job race), BIZ-2 (silent AI failure masking that operators cannot detect from the UI).

**Biggest architectural risks:** inconsistent application of an otherwise-correct RBAC pattern (AUTH-2/API-1/AUTH-3 are all instances of the same root cause: authorization enforcement living in some layers but not others); dependency-manifest drift (REL-3) as an infra landmine.

**Production blockers:** AUTH-1 and AUTH-2 must be fixed before any production deployment with real customer data across multiple organizations or multi-project field teams. REL-2 should be fixed before field engineers rely on the app in low-connectivity conditions, given it causes silent, unrecoverable photo loss.
